你此刻打开的这个网站就是作品本身。

这个站点的创建目的是保存个人笔记。域名注册于 2014 年，前身能追溯到更久之前。

## 网站前身

当时有很多提供个人博客的网站，比如面向程序员的博客园、CSDN 等，它们都能满足保存笔记的需求。
如果使用这些网站，万一它们将来停服或者有别的计划，我对自己的笔记可能失去掌控。
此外它们在笔记页面上插入广告，我却作为笔记的提供者却得不到任何收益。

因此一直寻求更好的保存笔记的方法。

最早可能是在 2010 年，那时候还在学校上学。
我依稀记得，当时接触到一个生成纯静态博客的方法，随即从每个网页上摘元素，凑出一个教学绿板风格的网站。
后来还用过新浪推出的一个轻网页托管服务。当初应该是没搞清楚原理，现在完全想不起来操作细节，技术和工具的名字都忘了。

大概由于在学校里的那一次折腾，2011 年参加工作后，习惯用 vi 记录纯文本笔记。

但是没有形成一个稳定的记录方法，断断续续地维持着，笔记七零八落。

## 初遇 Jekyll

好像是在 2014 前后，看到一个关于 github page 的介绍。

立马激灵起来，这不正是我最想要的笔记保存方式么！

* 在 vi 编辑器里用纯文本的方式记录，所有素材都在本地，始终拥有 100% 的掌控权。
* 在 git 仓库里保存，不容易遗失。
* 能直接转换成网页，而且网页样式可自由定义，可以开通 google 广告！

随即搭建起这套使用 jekyll 的笔记管理、发布方法，使用至今。

网页样式进行过多次调整。

每次都是临时看一点基础知识，然后东拼西凑的从各个网站上找元素，过程很痛苦。

平常看到各式网页习以为常，自己来设计的时候，才发现既不知道想要表达什么、又不知道如何表达。
别人的网页看似平平无奇，自己写的 html 展示出来后，才知道网页想要好看，布局、边框、阴影、行距、颜色、字体等里面藏着无数的细节。 

最终好赖写出一个满足基本要求的网页样式，一直用了好多年。

因为每次调整网页设计都会占用远远超出预期的时间，不想折腾了。

## 重新设计

重新设计的契机来自于 AI 大模型。

AI 大模型出来以后，曾经阻碍我表达的障碍消失了！

那些令网页好看的无数细节、实现各种各样动效的具体方法，再也不会让我焦头烂额、迷迷糊糊。
AI 不仅独立搞定具体实现，创作出的页面还审美在线，至少比我苦哈哈用很长时间画出来的好太多。

于是我决定重新把网站设计一下，之前的设计真的是仅仅能用来看笔记内容。

我还有很多想要但又模模糊糊说不清楚是啥的东西。

## 新版的设计思路

现如今你看到的这个网页，就是重新设计的结果。

所有的编码工作都是 AI 完成，但依然耗费了我整整四天的时间。

AI 确实能快速给出一个看得过去的结果，但是还是有不少展示的细节或者操作的方式，让我感觉不够舒服不够理想。
对于一些既想要这个又想那个的矛盾，AI 也常常给不出让我满意的处理方式。

几个细节调整，经常不知不知觉地耗费了2～4个小时。
一些矛盾的处理耗时甚至不可预期。因为 AI 给的方法可能越来越偏颇，常常经过各种胡乱操作后，自己才会突然在某一时刻想到解决的方法。

对于经验丰富、储备了各种方案的产品经理或者设计师而言，这个站的设计应该很小儿科。

对我而言，考虑到把内心模糊想要的东西澄清的过程、细节调整和矛盾处理耗费的精力、以及文案选择时的纠结，这个站还算是个作品。

### 设计起点

第一版由 AI 完成，初始提示词如下：

```
帮我设计一个用于展示个人信息的jekyll静态站，需要满足以下几个要求：
1. 首页上既能突出的展示我的经历简介、个人作品（app/网站等）、又能提示最新的Blog；
2. 需要有一个笔记目录、里面是各种不是成型的文章，包含改版之前的老文章；
3. 我期望着有人看到这个网站对我的作品和想法产生兴趣，会主动阅读历史文章；
4. 在web端和手机端都有很好的展示效果。
```

AI 给出的第一版设计和现在的这个网站差别很大，但是解决了从 0 到 1 的问题。

有了一个可见之物后，内心想要的事物的模糊面貌，在各种不对劲的分析过程中清晰起来。
那种模糊的、无法表达的感受，逐渐变成具体可指的问题。有了问题，就有了答案。

### 包含 Rail 的三栏设计

网站整体结构采用三栏设计，从左往右依次是：Navigation Rail、中间栏、内容区。

我期望在看一篇文章的时候，页面上能同时展示相关文章的链接，方便快速查看文章列表以及切换。
飞书文档的设计最让我满意，侧边栏显示文档目录，右侧大块无暇区域展示内容。
就是知识库的形式太像资料库，而不太像个人网站，无法引发对其它文章的兴趣。

误打误撞找到了左侧永久呈现极窄侧边栏的方式（AI实现后才知道这个叫做 Nav Rail/导航轨）。
加上导航立马有了个人网站的感觉，每个一个网页上都会提示用户，本站还有XX类目，吸引用户点击。

### 中间栏的内容设计

中间栏呈现的内容费了不少心思，在不同类型页面上，中间栏呈现不同内容。

**网站首页·中间栏**：留空，因为要凸显首页里的介绍内容、最新动态。

我想要给用户留下的第一印象，通过首页内容区达成。中间栏里如果有文字，会分散用户的注意力。
中间栏清空后，用户能把注意力全部放在内容区，有利于产生我期望的印象。

**栏目首页·中间栏**：展示栏目内标签，按照文章数量从高到低排序。

起初栏目首页的中间栏展示的是文章目录。对于栏目首页而言，主内容区显然更适合展示栏目内文章目录，用户能在更大的空间里仔细看栏目里有哪些文章。
如果主内容是文章目录，中间栏也是文章目录，给用户传达了重复的信息，且有主次不清的别扭感觉。

想过直接去掉栏目首页的中间栏。但是文章内容页是必须有中间栏的。如果进入文章内容页时中间栏显示，返回栏目首页时中间栏又消失，视觉上会很不舒服。
后来突然想到，对于栏目首页，中间栏里正好可以放栏目内标签。

展示标签的想法不是凭空冒出来的。在这之前试图在栏目页内容区的上方展示标签，方便用户通过标签筛选文章。
但是因为标签可能会非常多（比如笔记栏目），在主内容区头部怎么设计都很别扭，标签栏、标签云都不理想。
恰巧又对栏目页中间栏里的文章目录感到别扭，这才突然想到把标签放在中间栏里，一举解决了两个问题。

这个解法还对文章页产生了影响。

**文章页·中间栏**：展示当前文章的标签，点击呈现同标签里的文章目录。

起初文章页的中间栏是文章所在栏目里的文章目录，目的是解决快速切换文章的需求。文末显示文章标签，起到引导用户阅读更多文章的作用。
后来受到栏目页中间栏展示标签的启发，意识到在中间栏显示当前文章的标签，是更好的解决方法。

中间栏展示标签筛选后的目录，和当前文章内容相关性更高，切换阅读的概率更大。

这一设计同时起到方便切换文章和引导用户阅读更多文章的作用。一举双得的解法，效果比“中间栏显示全目录+文末显示标签”还要好。
一篇文章的标签不会特别多，采用 tab 设计外加纵向空间充足，查看同标签下文章更加方便。
原本被标签占用的页面底部空间释放，内容页底部更清爽。

### 内容区设计

内容区也是按照页面性质呈现不同的内容。

**网站首页·内容区**：呈现网站信息、最新动态等，力求让用户一目了然，产生印象。

现在的排版是反复优化了很多次的结果，很多琐碎的细节。比如最新动态里的分组设计，看起来特别简单，调整过程耗费了大约一天的时间。

**栏目首页·内容区**：按年份分组的栏目内文章目录（作品页因为内容特殊，采用不同形式）。

按年份分组也是突然想到的。原本计划归档目录承接旧版网站中的笔记，后来感觉没必要单独设计一个归档。
归档是在暗示用户没有必要阅读。把归档中按年份分组目录的方式，用在了栏目首页的内容区。

**文章页·内容区**：在展示文章内容之外，加了两个小设计，右侧的页内导航、左上角的返回按钮。

页内导航无需多言，查看超长的文章时，页内目录导航非常有用，既能一看看清文章结构，又能方便快速切换。

内容区左上角的返回按钮，纠结了好一阵，感觉还是非常有必要。
用户从栏目页内容区内进入文章后，很有可能习惯性回到进来时的位置，这时候有个返回按钮就非常方便。

## 设计无关的部分

这部分内容主要和 jekyll 的使用相关。
比如利用 jekyll 的 collection 、_data、_include、_layout 等能力，让站点配置更容易，修改管理更方便等。
事情太锁碎、无法也无必要阐述。稳定使用一段时间后，或许可以抽出一个 jekyll 模版。

## 收工感悟

这个网站最主要的设计就是上面提到的内容。
做完以后审视，其实一共也就是那么几个设计而已，只看结果真是没有什么难度。
但是把这个结果整出来的过程，一点都不轻松。

AI 确实提高了效率。
如果没有 AI，我可能要去啃各种 css/js/browser 的各种知识，反复踩各种坑。学习排版、练习审美，更非一日之功。

AI 不会让人更轻松。
AI 产出很快，产出问题的速度也加快了。特别是 UI 方面，一次产出会抛出好多个让人感觉不太对劲的地方。
大脑在同一时刻收到更多需要感受、分辨的不适感，思考的强度反而更大了。
